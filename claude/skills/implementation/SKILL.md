## Orden de ejecución (fase por fase)

### Fase 1 — Models, Enums, Contracts
- Crear/actualizar entidades JPA en `models/` con `@Entity`/`@Table`/`@Column` (namespace `javax.persistence`, NO `jakarta.*`), no-arg constructor `protected` y campos no-final. Setters solo donde el service deba mutar; mantener la superficie de mutación en la capa de service (controllers y vistas no mutan estado de entidad). FKs como `@ManyToOne`/`@OneToMany` en `LAZY` por default (entidad, no `Long xId` pelado).
- Crear/actualizar enums en `models/.../enums/`. Si se usan en BD, confirmar que se persisten con `.name()`.
- Actualizar interfaces de DAO en `persistence-contracts/` y de service en `service-contracts/` con las nuevas firmas. Toda firma nueva tiene que aparecer en su contract.

### Fase 2 — Persistencia
- Cambios de schema de producción → **nueva migración Flyway**: `persistence/src/main/resources/db/migration/V<N>__descripcion.sql` (PostgreSQL). NO existe más un `schema.sql` de producción y NO se edita una migración ya aplicada.
- Actualizar en paridad el schema de test HSQLDB `persistence/src/test/resources/schema.sql` (`INTEGER GENERATED BY DEFAULT AS IDENTITY`) para que el schema migrado y el de test queden funcionalmente equivalentes.
- Implementar DAO `*JpaDao` con `@Repository`:
  - `EntityManager` inyectado con `@PersistenceContext`.
  - Default `LAZY` en cada `@ManyToOne`/`@OneToMany` (un `EAGER` en cascada dispara 100-200 queries = error grave).
  - Listados paginados con relaciones → modelo 1+1 (native/JPQL de IDs paginados, luego JPQL con `JOIN FETCH ... WHERE id IN (:ids)`) para evitar N+1 y no traer la tabla a memoria.
  - Contadores derivados con `@Formula`, no un campo escrito por varios DAOs. `.size()` sobre colección lazy materializa todo → usar `COUNT(*)` o `@Formula`.
  - Paréntesis explícitos en `OR`/`AND` mezclados en HQL/SQL.
  - Ver `docs/hibernate-migration.md`.
- Tests de DAO (JUnit 5 + Spring) — NO usar `@Sql`; fixtures de lectura en `populator.sql`, preconditions de write con `JdbcTemplate` directo (nunca vía el DAO bajo test), asserts de write con `JdbcTestUtils.countRowsInTableWhere(...)` y `em.flush()` antes del assert:
  ```java
  @Rollback
  @Transactional
  @ExtendWith(SpringExtension.class)
  @ContextConfiguration(classes = TestConfiguration.class)
  class XxxJpaDaoTest {
      @PersistenceContext private EntityManager em;
      @Autowired private DataSource dataSource;
      @Autowired private XxxDao dao;
      private JdbcTemplate jdbcTemplate;

      @BeforeEach void setUp() {
          jdbcTemplate = new JdbcTemplate(dataSource);
      }

      @Test void createsRow() {
          // 1. Arrange · 2. Exercise (dao.create(...)) · em.flush()
          // 3. Assert con JdbcTestUtils.countRowsInTableWhere(jdbcTemplate, TABLE, "cond exacta")
      }
  }
  ```

### Fase 3 — Services
- `@Service` + `@Transactional` (o `readOnly=true` en queries).
- **Ownership declarativo en la capa web**: la decisión vive en `@PreAuthorize` sobre el método del controller, backed por un access handler en `webapp.auth`. El service NO toma decisiones de ownership ni tira `ForbiddenException` como barrera primaria; puede exponer una *query* booleana (`isProvider`, `isOwner`) que consume el handler. El service carga el recurso (`getById` / `findById`) y tira `ResourceNotFoundException` (404) si no existe. Ver `docs/security.md`.
- Un service inyecta solo su propio DAO; para datos de otro agregado, depende del service responsable, no del DAO ajeno.
- Todo método público tiene que estar en la interface (`service-contracts`).
- `ResourceNotFoundException` y `ForbiddenException` viven en `service-contracts` (`ar.edu.itba.paw.services.exceptions`); el mapeo HTTP lo hace `GlobalExceptionHandler`, no `@ResponseStatus`.
- Tests de service con Mockito (solo si hay lógica real, no para pasamanos):
  ```java
  @ExtendWith(MockitoExtension.class)
  class XxxServiceTest {
      @Mock private XxxDao dao;
      @InjectMocks private XxxServiceImpl service;

      @Test void createsXxx() {
          when(dao.create(...)).thenReturn(...);
          Xxx result = service.create(...);
          assertEquals(..., result.getField());  // behavior, no verify()
      }
  }
  ```
- **PROHIBIDO** `Mockito.verify()` y `Mockito.spy()`.

### Fase 4 — Custom Validators (cuando aplica)
- Anotación en `webapp/validation/annotations/Xxx.java`:
  ```java
  @Constraint(validatedBy = XxxValidator.class)
  @Target({ FIELD, TYPE }) @Retention(RUNTIME)
  public @interface Xxx {
      String message() default "{validation.xxx}";
      Class<?>[] groups() default {};
      Class<? extends Payload>[] payload() default {};
  }
  ```
- Validator en `webapp/validation/validators/XxxValidator.java` implementa `ConstraintValidator<Xxx, Tipo>`, inyecta un **Service** (no DAO) con `@Autowired`.
- Cross-field: anotar la **clase** del form y usar `addPropertyNode("campo")` para atar el error a un campo específico.
- Agregar keys en `messages_es.properties` y `messages_en.properties`.

### Fase 5 — Controllers y Forms
- Form object en `webapp/form/` con getters/setters + anotaciones JSR-303. **No reutilizar entidades del modelo.**
- Controller con `@Controller`:
  - `@Autowired` en field para services (convención del repo) o constructor.
  - `BindingResult` **inmediatamente** después de `@Valid`.
  - Error de validación → `return index(form)` (no redirect).
  - Éxito de POST → `redirect:/ruta`.
  - Cero try/catch: dejá que las exceptions lleguen a `GlobalExceptionHandler`.
  - Cero lógica de dominio: delegá al service en una línea.
- Query params de GET (filtros/paginación): validación manual con clampeo. `if (page < 1) page = 1;`.
- Si se lanzan exceptions nuevas, confirmar que `GlobalExceptionHandler` las mapea a 4xx apropiado.

### Fase 6 — Vistas JSP
Por cada `.jsp` en `WEB-INF/views/`:
- Taglibs al inicio: `c`, `spring`, `form`, `sec` (si hay roles).
- `<c:out value="${var}" />` en **todo** texto de usuario/BD. No crudo.
- `<c:url>` en href/src/action, con `var=` si se reutiliza.
- `<form:form modelAttribute="xxxForm" action="${path}">` — el nombre debe matchear el controller.
- `<form:errors path="campo" cssClass="formError" element="p" />` por cada campo.
- `<spring:message code="..." />` para todos los textos visibles. Keys nuevas en ambos `messages_*.properties`.
- `<sec:authorize access="hasRole('XXX')">` para UI condicionada por rol.
- Reutilizar custom tags de `WEB-INF/tags/` cuando haya uno aplicable.

## Reglas de estilo (innegociables)

- **DI por constructor** preferido; si el archivo existente usa field injection, seguí el estilo del archivo.
- **Modelos**: entidades JPA (`@Entity`) con no-arg constructor `protected` y campos no-final; setters solo donde el service deba mutar, sin que controllers/vistas muten estado.
- **JPA/Hibernate**: DAOs `*JpaDao` con `EntityManager`; default `LAZY` en relaciones; modelo 1+1 para paginación con relaciones; FKs como entidad, no `Long xId` pelado; `@Formula` para contadores derivados; namespace `javax.persistence`.
- **No scriptlets** en JSP. Solo JSTL + EL.
- **Tests de behavior**, no de implementación. Sin `verify()`, sin `spy()`. DAO tests con `em.flush()` antes del assert.
- **Naming**: interfaces sin prefijo `I` (`UserService`, no `IUserService`); enums en `UPPER_SNAKE_CASE`; constantes `private static final`.
- **Schema SQL en archivos `.sql`**, nunca en código Java: migraciones Flyway (prod) + `schema.sql` de test HSQLDB.
- **Locale de emails**: `recipient.getPreferredLanguage()`, no `LocaleContextHolder`.
